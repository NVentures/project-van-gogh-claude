## Why this contract looks like this

A red-team pass ran against the first draft and changed it substantially. Its
finding: the draft proved the plumbing exists on the developer's machine with
the developer's data, and proved nothing about whether the output is correct on
anyone else's. Concretely, it predicted that a client who writes priorities as
intentions ("grow the pipeline") rather than things ("Close QX Corp") gets an
almost empty urgent section, a briefing that looks calm and finished, and a
contract deadline sitting one section below where they stopped reading. Every
criterion in the draft passed in that scenario.

That finding is accepted, and it is why P4 through P8 exist and why the work in
Phase 3 includes a design change rather than only verification.

Nobel's direction on the fix: keyword determinism cannot carry this judgment.
The relevance call is made by an Opus-class model that reads the user's actual
priorities and the actual item, with deterministic code keeping the rails.
Model decides relevance; code decides what is allowed to happen with that
decision, and every safety guarantee stays in code. Approved 2026-09-03
with Opus as the judge model, configurable per install.

- [ ] P1. `app/priority_judge.py` exists and judges an item's relevance to a bucket's stated priorities semantically, not by string overlap. - [ ] P2. The model can never invent a bucket or a priority. - [ ] P3. Model failure fails SAFE, never silent. On a non-zero exit, timeout, unparseable output, or quota message, the judge returns a degraded result flagged `degraded: true`, the deterministic matcher is used instead, and NO demotion happens on that run. The briefing says the judgment layer was degraded rather than rendering a confident section built without it. | verify: tests stubbing each of the four failure modes; assert `demoted == []` and the degraded flag reaches the rendered output | proof: test output + a rendered briefing carrying the degraded notice

Two deterministic guards hold regardless of what the model says: (a) if NO item in a bucket was judged relevant to any of that bucket's priorities, nothing in that bucket is demoted (the priorities are worded in a way the layer cannot read, so it must not hide anything); (b) an item carrying an explicit date or deadline is never demoted. | verify: tests for both, plus a test proving each guard fires independently of the other | proof: test output
- [ ] P5. Every demotion carries a human-readable reason that names the bucket and the priorities it was judged against, and that reason reaches the rendered briefing. ## Lessons

Recorded 2026-09-03, after five evaluation rounds and three focused re-grades.

**A check blind to one spelling of its target is worse than no check.** This
happened four separate times in one review, and every time the check printed a
confident zero that got believed: a surname pattern requiring three letters
(so "Kevin Yu" was invisible), a doubled backslash (so no Windows path could
ever match), a hyphen (so "pd46-energy" walked past a deny list that knew
"pd46energy"), and a word boundary before an underscore (so every variable
named the way this product names them defeated the secret redactor). The rule:
a new scanner must find a PLANTED instance of every class it claims to cover
before its zero means anything, and the plant has to include the shapes it is
suspected of missing, not the ones it already handles.

**Planting only what already works is how a check ships blind.** The secret
scan planted one shape, the one the redactor was known to catch, so it could
not fail. Three rounds of leaks passed under it. A negative check needs its
plants drawn from the threat, not from the implementation.

**A gate tests a property somebody thought of.** Twenty-nine contract items,
ten verification scripts and 734 tests were green when a stranger was handed
the rendered page and found, in ninety seconds, that it said "nothing moving
on this" about a priority while holding the exact item that moved it. The
cold read cost four minutes and was the highest-yield check in the whole
review. The single best question of the five: does anything contradict
anything else.

**Read the exit code of the script, not of the pipeline.** A round-6 finding
claimed the safety check exits 0 on failure. It came from `cmd | tail; echo $?`,
which reports tail's status. Verified by running the script alone. This is the
same POSIX footgun already recorded in lab notes for `cmd | tee`.

**Verify a claim from another agent before acting on it.** Two of the
evaluator's findings did not survive checking: the exit-code claim above, and
a "leak" that was its own needle extraction splitting on "=" and producing an
empty string, which is present in every text. Both were reported as defects
and neither was one. Everything else it found was real, including the four
worst defects of the review.
